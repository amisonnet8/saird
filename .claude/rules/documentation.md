# ドキュメントの書き方

## 言語

- **コード・コメント・CLI の出力は英語。** `CLAUDE.md`・`.claude/rules/`・mtqg の記録は日本語
- **`docs/`と`README.md`は、今は日本語だけ。** 公開の前に、英語を正本（`*.md`）にし、今の日本語を`*_ja.md`に移して整える。2本立てにしたあとは、片方だけを直さない（同じ変更の中で両方を直す）。いつ2本立てにするかは人間が決める
- crube の説明は英語と日本語の両方（`.claude/rules/crube-usage.md`）

## 書き方

- 断定の文体（〜である／〜する）
- 経緯や名前の由来は書かない
- シンプルさを優先する。機能を足すより、曖昧さを消す定義を優先する
- 新しい用語は`docs/reference/glossary.md`に一言の説明を付けて加える
- 既存技術を使うときは名前を挙げる

## `docs/`は仕様

`docs/`は Saird の仕様。

- **AI が`docs/`を直すのは、人間の依頼があったときだけ。** 直すときは、同じ変更の中で関係する文書と`docs/examples/`も直す
- **実装の作業中に、仕様の誤り・矛盾・曖昧さ・実装できないところを見つけたら、直さずに人間に聞く。** どこが・なぜかと直し方の案を添え（`.claude/rules/working-with-human.md`「重要な判断」）、`mtqg q add`に残す
- **実装が仕様と違う振る舞いをしていたら、実装の不具合**（`mtqg b add`）。仕様に合わせて実装を直す
- 仕様に書いていない実装の細部（エラーメッセージの文面、内部の構成など）は実装の判断。mtqg に残す
- `CLAUDE.md`「文書と今のコードが食い違うとき」は、コードの**書き方**（命名・構成・エラーの扱い・テストの形）の話。**振る舞い**は、上のとおり仕様が正
- 仕様の版は`CLAUDE.md`にある。版を上げるかは人間が決める
- 実装の文書（使い方・コマンドの説明など、仕様でないもの）を`docs/`に足すときは、置き場所を人間に聞く

## 例の値

- **docs の例の値（ハッシュ・出力・件数など）は、推測で書かず、道具で求めるか、実際に動かして確かめて書く**（`.claude/rules/testing.md`「期待値は、テストを書く前に決める」と同じ考え方）。実装より先に docs を書くときも同じ
- 例はコードブロックで書く。あとで「docs の例と実際の出力を突き合わせるテスト」を足せるように、機械で読める形にしておく

## 経緯は mtqg に書く

`docs/`には今の仕様だけを書く。経緯、捨てた案、途中で直した履歴は、mtqg に記録する（`.claude/rules/mtqg-usage.md`）。
